## Dependency Version Conflict Analysis

### quic-go/quic-go vs qpack Version Matrix

| Package | Version | qpack Dependency |
|---------|---------|-----------------|
| github.com/quic-go/quic-go | v0.54.0 | qpack@v0.5.1 (expects) |
| github.com/quic-go/qpack | v0.6.0 | N/A |
| github.com/sagernet/sing-quic | v0.6.1 | qpack@v0.6.0 |
| github.com/sagernet/sing-box | (root) | qpack@v0.6.0 |

### Resolution Path Analysis

The conflict arises because:
1. sing-box root requires qpack@v0.6.0 (via go.mod)
2. quic-go@v0.54.0 internally requires qpack@v0.5.1

**Not directly resolvable at sing-box level** because:
- quic-go is an indirect dependency through sing-quic
- quic-go v0.54.0 is pinned by upstream sing-quic v0.6.1
- Cannot override without modifying sing-quic dependency chain

**Options for resolution** (outside scope of this merge):
1. Upgrade quic-go to a version compatible with qpack@v0.6.0
2. Downgrade qpack requirement in sing-box root
3. Fork quic-go and adapt to qpack@v0.6.0

### Which packages trigger the quic-go build failure?

Packages that transitively depend on quic-go/http3:
- protocol/hysteria2 (uses sing-quic which uses quic-go)
- protocol/naive (uses quic)
- Any package using quic-go directly

### What would break if we removed the qpack replace?

The replace directive:
```
replace github.com/quic-go/qpack => github.com/sagernet/quic-go/qpack v0.6.0-sing-box-mod.4
```

This replace redirects all qpack imports to sagernet's fork. Without it:
- sing-box code that directly imports qpack would use the wrong version
- The quic-go build would still fail anyway (internal dependency conflict)

## tlsfragment Test Analysis

### Test Failure Details
```
TestTLSFragment
conn_test.go:21: Received unexpected error: tls: first record does not look like a TLS handshake
```

This is a test that attempts to do a TLS handshake with a mock connection. The failure indicates:
1. The mock is sending data that doesn't look like a valid TLS ClientHello
2. This is likely a timing or initialization issue in the test mock

### Production Impact: NONE
- This is a unit test in common/tlsfragment
- The tlsfragment package itself builds fine
- Production code paths don't exercise this test
